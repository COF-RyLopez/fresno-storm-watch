1. Publish the GitHub Pages prototype

  1. Choose the repository owner. Use the county's approved GitHub organization or your approved pilot account. Suggested repository name: fresno-storm-watch. This package contains only public source data and application code; upload this package, not the surrounding storm project workspace.
  2. Extract the ZIP and open its folder. The repository root must directly contain package.json, site, scripts, tests, and the hidden .github folder. Do not upload the ZIP itself as the application.
  3. Create the repository. In GitHub, create an empty repository with the chosen name. For GitHub Free, use a public repository. A private repository needs a plan that supports Pages for private repositories; the Pages website can still be public. See GitHub Pages availability and private Pages requirements.
  4. Upload using Git. Open PowerShell in the extracted folder. Replace OWNER in the last two lines below with your GitHub organization or account. Git may open its normal sign-in flow. Do not paste a token into these commands.
git init -b main
git add .
git commit -m "feat: add Fresno Storm Watch prototype"
git remote add origin https://github.com/OWNER/fresno-storm-watch.git
git push -u origin main

If Git asks for your author identity, configure your approved work name and GitHub email locally for this repository, then repeat the commit. If using GitHub Desktop, add this folder as a local repository after git init, commit the files, and publish to your chosen owner instead of adding/pushing a remote by hand.

  1. Enable deployment. In the repository, open Settings → Pages → Build and deployment → Source → GitHub Actions. Allow GitHub Actions if your organization requires administrator setup. The included workflow tests the app and uploads only the site directory. See GitHub's custom workflow documentation.
  2. Run the workflow. Open Actions → Verify and deploy Storm Watch → Run workflow → main. If the first push ran before Pages was enabled, rerun its failed job. Wait for both verify and deploy to pass.
  3. Open the published address. Use the exact URL displayed under Settings → Pages, normally https://OWNER.github.io/fresno-storm-watch/. Open it in a signed-out browser and verify the map and regional query timestamp. Save this final address for ArcGIS registration.

The app's code and bundled county boundaries are public website files. ArcGIS sign-in does not make those files private. Future private operational data must remain in services that enforce each user's permissions. This prototype has no private datasets or task-writing integration.

2. Enable optional county ArcGIS sign-in

Deploy the public view first. Then register the final Pages URL using an account that can create content in county ArcGIS Online.

  1. In Content → My content → New item → Developer credentials, select OAuth 2.0 credentials — For user authentication. Some roles go directly to the OAuth options.
  2. Add the final Pages address as a redirect URL. Also add its index.html variant if people will use that address. For local testing, optionally add http://127.0.0.1:8777/. Use your actual hostname and repository path.
  3. Set the app URL to the Pages address. Name the item Fresno Storm Watch — Prototype, choose its content folder, review the summary and create it. Find the Client ID in the credential settings. If these options are unavailable, ask the AGOL administrator to register the app.

These steps follow Esri's user-authentication registration instructions. Redirect URLs must match the registered address.

  1. In this package, edit site/config.js. Put only that public Client ID between the quotes in clientId: ''. Leave portalUrl pointing to county AGOL. No client secret, password or access token belongs in the repository.
  2. Commit and push the one-file change. After deployment passes, reopen the live Pages address and click County ArcGIS sign-in. Authentication occurs on the ArcGIS page. The prototype should return showing the account username.
  3. Test Sign out, canceled sign-in and a second authorized account. Public alerts should remain usable. Record the browser, deployment commit and outcome. Until this succeeds, mark sign-in unverified.

The code uses the SDK's authorization-code flow with PKCE and a full-page redirect. No separate callback file is required for this configuration. See OAuthInfo and the official identity sample. Registration is configured for this deployment. The EOC workspace reads private exercise records after sign-in and checks assigned groups before offering edits; AGOL enforces access. Confirm reviewer eligibility and complete the two-account acceptance exercise.

County 3D companion: enable photorealistic imagery

Current status, checked October 17, 2026: F.R.O.G. — Fresno River Context 2026–27 is saved in the Storm Operations 2026-27 folder and connected to the app. It uses Esri terrain, a topographic basemap and FEMA reference. It is shared with Storm Operations 2026-27 - Authorized viewers, not publicly. Google Photorealistic 3D was not present in the signed-in county basemap gallery and is not active yet.

Esri currently supports its photorealistic preview in hosted ArcGIS apps, with named-user access. Custom-app support is still planned. We therefore open the official county Scene Viewer in a separate tab. See Esri's June 2026 availability notice.

  1. County AGOL administrator: open Organization → Settings → Map and scene. Under Google Photorealistic 3D basemaps, confirm the county's entitlement and available sessions, then enable Allow members to use Google Photorealistic 3D basemap. This is an administrator task; the app does not change it. Esri configuration instructions.
  2. Scene author: in Storm Watch, locate a gauge or camera, open the map, then select County 3D → Open county 3D companion. Sign into county AGOL with access to the pilot viewers group. The saved scene opens at approximately the current map area. Use Basemap to choose Google Photorealistic 3D. If absent, return to the administrator step.
  3. Check coverage: inspect the San Joaquin at Highway 41, Friant/Millerton, Gravelly Ford, James Bypass, and Kings River below Pine Flat. Confirm detailed mesh exists at each location; rural coverage and image age can vary. Check FEMA overlay alignment and attribution. Keep terrain available where mesh coverage is absent.
  4. Save the existing scene: update the companion item after selecting and checking the basemap. Its item ID is already connected. Retain pilot-group sharing and test with a named member. Add reviewed reference layers and useful slides as needed.
  5. Update readiness after verification: set arcgis.photorealisticVerified to true in site/config.js only after confirming the saved scene loads the mesh. Commit and push. If a replacement scene is ever required, update arcgis.photorealisticSceneId too. An item ID does not grant access. No password, token or OAuth secret is required for the launcher.
  6. Acceptance: open the companion from two river locations in both 2D and 3D. Confirm its location, Google imagery, source credits, sign-in and sharing behavior. Verify that returning to the Storm Watch tab preserves live feeds. The launcher transfers the camera when opened; it does not synchronize gauges, camera media, alert status or later navigation.

The launcher uses Esri's documented Scene Viewer URL parameters. This companion includes FEMA's full layer and shows it at local zoom levels; it does not reproduce Storm Watch's selected-zone or Fresno display filters. Scene layers, styles and filters are maintained separately.

If the mesh must run inside GitHub Pages: a separate Google Maps Platform integration can use ArcGIS IntegratedMesh3DTilesLayer with Google's Map Tiles API. That route requires a county Google Cloud project, enabled billing, an API-restricted and website-restricted browser key, usage limits and attribution. It is not configured or activated in this release. Do not send credentials in chat.

Photorealistic imagery is visual context. It is not live flood imagery, a surveyed hydraulic terrain model, a bridge opening survey or proof that a staging route is passable. Its availability does not alter the notification rules.

3. Verify before sharing the prototype

For 3D and cameras: choose SR-41 Avenue 9, use Locate on map, then 3D terrain. Confirm the camera, Highway 41 gauge and FEMA polygons remain visible at local zoom. Try Imagery, Overhead and 2D. Play live video and confirm motion/time advance, then close Cameras and confirm playback stops. Reopen it: video must require Play again. Try another camera and inspect image file time versus app load time. A stream failure must retain the still-image option. Camera views may show only highway conditions.

For weather and reservoirs: open Weather & reservoirs. Select Radar, then an older frame and Latest. Check the timestamp against NWS. Select Rainfall forecast and test all three periods; compare the issue and valid window with WPC, then click a polygon for its source value. Switch 2D/3D and confirm the selected overlay persists. Compare Millerton storage, river outlet release and Pine Flat outflow with their CDEC links. Daily and hourly values must retain separate dates/times and units. Check that missing/newer records are labeled and no total Millerton outflow is called river release.

  • Open the live view while signed out. Confirm nine candidate Fresno watchpoints and the observation/forecast coverage counts. Open Gravelly Ford, Trimmer and Little Dry Creek; compare values, units, observation times and forecast issuance with each official gauge page. Missing values and thresholds must remain unknown.
  • Change the forecast window and river group. The window must change the sampled forecast high; the group filter must not change the overall watchpoint counts. Open a gauge and select Inspect FEMA vicinity. Check a polygon's zone against its official FEMA record. This overlay is not a forecast-derived inundation boundary.
  • In the fictional exercise, try Threshold crossing, Old river data and Station failure. Check that old or failed records cannot produce a current threshold cue and previous values are labeled old/unverified. River baseline restores the exercise.
  • Keep the live tab visible for more than five minutes. The river last-attempt time and an individual gauge's last-station-query time should advance. An attempted query alone is not proof of success.
  • Switch to Weather alerts. Confirm all five county outlines and NWS source links. An empty regional result must say “No alerts returned.”
  • Keep the tab visible for more than five minutes. “Last successful regional query” should advance without reloading. A browser may suspend background tabs; the app checks again when an overdue tab becomes visible.
  • Open the fictional exercise. Clear the initial notice, add a warning, clear it, and publish a new revision using the exercise buttons. Confirm a fresh notification appears.
  • Use Baseline / recover, clear notifications, then Duplicate polygons. The count should remain two without a fresh notification. Select an alert and confirm its label, issue time, expiration, counties and outline agree.
  • Use Feed failure. Previous counts and the previous successful-query time must remain, with a failure banner. Recover, then try Expired alerts and Empty result. Neither should declare conditions safe.
  • Pan or zoom the map and change the list filter. The regional counts and notification banner must remain independent of the map extent and list filter. Test on a phone as well as the EOC display.

Exercise mode makes no live NWS queries and uses fictional records. Return to the live view before relying on publisher data. Clearing a notification changes only this open tab; it is not a team acknowledgement, hazard cancellation or saved review.

Google Photorealistic 3D Tiles: optional next integration

The custom app can use Google's direct Map Tiles API through the ArcGIS SDK's IntegratedMesh3DTilesLayer in its existing 3D view. Esri's product-team guidance distinguishes this visualization-only custom route from ArcGIS applications with analytical tools. The existing county-hosted 3D companion is retained. The direct Google service is not configured or tested with a key in this release.

  1. County Google Cloud owner: create/select an approved project, enable billing and the Map Tiles API. Confirm the county's intended usage and current agreement. Follow Google's setup. No ArcGIS extension provides this Google API entitlement.
  2. Restrict a browser key: restrict it to Map Tiles API and the production website https://cof-rylopez.github.io/*. Use a separate development key with only the required localhost origin. Browsers commonly send just the origin, so a repository-path restriction may fail; a dedicated county hostname offers tighter isolation. A browser key is visible to visitors and is not a confidential server credential. See Google key restrictions. Do not send unrestricted keys in chat.
  3. Cost controls: set a conservative daily root-tileset quota and billing alerts. Budget alerts alone do not stop spend. Check the current usage and billing rules; 3D sessions are charged through root-tileset requests. The proposed implementation loads only when the operator chooses Google 3D, with 2D/terrain fallback on quota or network failure.
  4. Implementation and acceptance: add the direct root tileset with the restricted key, verify Google's logo and dynamic tile-provider credits stay readable on desktop and phone, and test Fresno river corridors at street scale. Coverage and detail must be checked at actual sites; they are not assumed countywide. Preserve operational overlays as separately attributed data.
  5. Use as visual context: comply with Google's display, attribution and content-use requirements. No tile extraction, tracing, offline archive, derived terrain/flood modeling or image analysis. Existing public-source matching uses county points and utility polygons, not Google mesh data. Photorealistic imagery is not current flood, outage or access evidence.

4. Operate and iterate

Local development: install Node.js 22.22.3 or a compatible Node 22 release. In the package folder run npm test, npm run check, then npm start. Open http://127.0.0.1:8777/. No npm dependencies or install step are needed. Stop the local server with Ctrl+C.

Keep local reservoirs updating: in a second PowerShell window in the same folder, run npm run watch:reservoirs. This collects public CDEC data immediately and every 15 minutes while that process runs. For a single update, use npm run collect:reservoirs. Stop the collector with Ctrl+C. Reopening the browser alone does not start the collector. A packaged snapshot is dated data, not a running feed.

Enable hosted reservoir refresh: the included Pages workflow collects CDEC readings before deployment. After the initial publish, keep Actions and scheduled workflows enabled on the default main branch. The schedule targets minutes 07, 22, 37 and 52 each hour. Check Actions for successful Collect public CDEC reservoir readings and deployment steps, then verify the app's collection time advances. Use Run workflow for a manual refresh. No CDEC token or AGOL license is required. GitHub scheduled workflows can be delayed, dropped or disabled for inactive public repositories; account plan and Actions limits apply. No background delivery guarantee is implied. The app flags a snapshot older than 45 minutes.

Collector failure check: on a private QA copy, stop the collector and confirm the overdue notice after 45 minutes. A station request failure must preserve its old successful time and show the source error. Do not erase the timestamp or fill gaps with zero to make a feed appear healthy. The collector logs one structured summary per run; maintainers should review workflow failures and source-error warnings. There is no unattended operator paging.

What the app checks: complete county intersections, stable NWS identifiers and revision/content changes. It polls after five minutes while visible. It shows a late-query warning after seven minutes without a successful regional query. Query success proves a response was received; it cannot establish whether NOAA's underlying publication pipeline is current. Issue, expiration and ingestion times remain distinct.

Dependencies: NOAA alerts, NWPS gauges, MRMS radar and WPC QPF; DWR CDEC operator reports; FEMA NFHL; bundled Census boundaries; Esri SDK 5.1, public basemaps and terrain; Caltrans CCTV; bundled hls.js 1.7.3 and its license. Public sources poll independently. Failed reservoir collections retain explicitly dated previous values. Age checks are configurable prototype rules. A failed map does not stop text feeds. GitHub Actions can collect public CDEC data; GitHub Pages serves the resulting static snapshot. Private credentials, faster services and shared operational writes remain separate future components.

Updates: use a small branch and pull request for each source. The workflow checks pull requests without deploying them. Merging to main deploys after checks pass. Review the source register and run the exercise after SDK, feed or classification changes. Record the responsible county maintainer and backup in the repository's administrative records.

Rollback: use GitHub's Revert action on the last merged change, or git revert COMMIT locally and push. This creates a new deployment from the previous code without deleting history. The existing Experience Builder pilot remains available independently.

Next iteration: finish optional sign-in validation, then connect a selected read-only AGOL web map. Implement team review only after verifying the reviewer account's privileges and the private submission/results views. Keep live fleet locations and vendor credentials out of static GitHub files.
